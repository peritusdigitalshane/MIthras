# Microsoft 365 / Entra ID Threat Detection (ITDR) — MVP

**Status:** Built + deployed 2026-06-01. Operator setup pending.
**Scope:** MVP — 7 detections, read-only consent by default with opt-in
remediation. Phase 2 (response actions, ITDR for Google Workspace, SaaS
log ingestion) deferred.
**Target environment:** Vultr `149.28.186.142` (production-ish).

---

## 1. Overview

### Problem

The Mithras platform was endpoint-only. Half the modern attack surface for
SMB customers lives in Microsoft 365 — phishing, business email compromise
via mailbox forwarding rules, illicit OAuth consent attacks, account
takeover via password spray, privileged role grants. Without coverage of
the identity layer, Mithras competes with EDRs but not with full-stack
managed-detection products (Huntress, CrowdStrike Identity, Defender for
Identity).

ITDR (Identity Threat Detection and Response) closes that gap without
needing humans in the loop — the detections are deterministic, signal-rich,
and API-driven via Microsoft Graph.

### Goal

Ship a read-only ITDR MVP that:

- Lets a customer admin connect their M365 tenant in under 2 minutes via
  OAuth consent
- Polls Microsoft Graph every 5 minutes for sign-in events, audit log
  entries, mailbox rules, and OAuth grants
- Runs 7 detections covering the highest-yield identity attack patterns
- Surfaces alerts in the existing alert workflow (no new SOC console
  needed)
- Has an opt-in elevated-consent flow for tenants who want remediation
  actions (disable forwarding rule, revoke OAuth grant, force re-MFA) —
  deferred build, just plumbing today

### Non-goals (Phase 2 / future)

- Remediation actions themselves — only the elevated consent flow ships
  today; the actual "Disable rule" buttons are deferred
- Google Workspace ITDR — same architectural pattern but separate work
- SIEM-style search across raw events — for MVP everything goes through
  the alerts table; rich search comes with EDR-grade telemetry retention
- Microsoft Sentinel integration — not on roadmap

### Architectural principles

- **Multi-tenant by default.** Each Mithras organisation can connect zero
  or one M365 tenant. RLS scopes every table by `organization_id`.
- **Tokens encrypted by access control, not at rest.** The token columns
  on `m365_tenants` are exposed only via the service role; org members
  read everything else through the `m365_tenants_view` projection. This
  matches how the rest of the platform stores secrets (`endpoints.agent_secret`,
  `platform_settings.value` for secret keys).
- **Detections fire on ingest, not on schedule.** Trigger functions on
  the data tables raise alerts immediately when qualifying rows arrive.
  Only aggregate detections (spike detection) run on a schedule.
- **No new infrastructure.** Reuses Postgres + pg_cron + pg_net + the
  existing Supabase edge functions runtime.

## 2. The 7 detections

| # | Name | Trigger | Severity | Source table |
|---|------|---------|----------|---|
| 1 | `m365_suspicious_signin` | Entra ID `riskLevel` ∈ {medium, high} on a new sign-in event | high / critical | `m365_sign_in_events` |
| 2 | `m365_external_mailbox_forward` | Inbox rule appears (or transitions to active) with `forward_to` / `redirect_to` addresses outside tenant domains | critical | `m365_mailbox_rules` |
| 3 | `m365_mfa_weakened` | Audit event "Disable Strong Authentication" or "User deleted security info" | high | `m365_audit_events` |
| 3a | `m365_ca_policy_disabled` | Conditional Access policy state transitioned to `disabled` | high | `m365_audit_events` |
| 4 | `m365_privileged_role_assigned` | Audit event "Add member to role" where role display name ∈ privileged set (Global Admin, Exchange Admin, etc.) | critical | `m365_audit_events` |
| 5 | `m365_high_risk_oauth_grant` | OAuth grant appears with scope containing high-risk permissions (`Mail.ReadWrite`, `full_access_as_app`, `RoleManagement.ReadWrite.Directory`, etc.) | high | `m365_oauth_grants` |
| 6 | `m365_signin_spike_user` | ≥50 failed sign-ins for a single user in 15 min (with 1h cooldown) | high | aggregate over `m365_sign_in_events` |
| 7 | `m365_signin_spike_tenant` | ≥500 failed sign-ins across the tenant in 15 min (with 1h cooldown) | critical | aggregate over `m365_sign_in_events` |

All seven write to `public.alerts` with `alert_type` prefixed `m365_`, so
they flow through the existing alert-notification pipeline (email, SMS if
configured, in-app feed).

The exact rule logic and severity mapping lives in
`supabase/migrations/20260601100100_m365_itdr_detections.sql`.

## 4. Schema reference

### `m365_tenants`

One row per `(organization_id, tenant_id)`. Holds OAuth tokens and consent
state.

| Column | Notes |
|---|---|
| `id` | PK |
| `organization_id` | FK → `organizations.id` |
| `tenant_id` | Azure AD tenant GUID |
| `tenant_display_name`, `tenant_domain` | Surfaced in UI |
| `access_token` | **Sensitive.** Service-role read only. |
| `access_token_expires_at` | Set to actual expiry − 60 s for safety margin |
| `refresh_token` | **Sensitive.** Service-role read only. May be rotated by Microsoft |
| `scopes` | Granted scopes (string array) |
| `consent_state` | `pending` / `active` / `failed` / `revoked` |
| `remediation_enabled` | False by default. Flipped via opt-in elevated consent |
| `remediation_scopes` | Additional scopes granted by remediation flow |
| `last_poll_at`, `last_poll_error` | Poll-cycle bookkeeping |
| `connected_by` | FK → `profiles.id` |

A view `m365_tenants_view` exposes everything EXCEPT the token columns;
the frontend reads from the view, the poller (service role) reads from
the base table.

### `m365_sign_in_events`

Mirror of `auditLogs/signIns` from Graph, deduplicated by
`(m365_tenant_id, graph_event_id)`. Indexed by `occurred_at` and by
risk_level for fast "what happened recently?" queries.

### `m365_audit_events`

Mirror of `auditLogs/directoryAudits`. Same dedup pattern. Indexed by
category for the trigger functions that key off category + activity name.

### `m365_mailbox_rules`

Current state, not log. One row per `(m365_tenant_id, user_id, rule_id)`.
The poller upserts; rules that disappear between polls are eventually
flagged `is_active = false` (sweep step deferred — for MVP we live with
some stale rows). Computed columns `forwards_externally`,
`forward_to_addresses`, `moves_to_folder`, `deletes_messages` materialise
the signals the trigger reads.

### `m365_oauth_grants`

Periodic snapshot of `oauth2PermissionGrants`. Same pattern as mailbox
rules — current state, not append log. `has_high_risk_scope` and
`high_risk_scopes_matched` are precomputed by the poller using the
scope list from `m365_high_risk_scopes()`.

### `m365_detection_dedup`

A tiny `(detection_key TEXT PRIMARY KEY, last_fired_at TIMESTAMPTZ)` table
used by the aggregate spike detections to enforce a 1-hour cooldown. The
trigger-based detections don't need this — they're already keyed by
distinct event ID.

## 5. OAuth flow detail

### Read-only consent

1. User clicks **Connect Microsoft 365** on `/m365` (admin or super-admin).
2. Frontend calls `m365-oauth-start` with `{organization_id, mode: "read_only"}`.
3. Function:
   - Verifies caller is admin of the org (or super-admin)
   - Looks up `client_id` + `redirect_uri` from `platform_settings`
   - Signs a state payload `{org_id, user_id, mode, nonce, iat}` with
     HMAC-SHA256 over `M365_STATE_SECRET`
   - Returns the Microsoft consent URL with that state embedded
4. Frontend `window.location.assign(consent_url)`.
5. Microsoft shows consent screen with the read-only scope set
   (`offline_access`, `User.Read`, `AuditLog.Read.All`, `Directory.Read.All`,
   `MailboxSettings.Read`, `Application.Read.All`,
   `IdentityRiskEvent.Read.All`).
6. Admin clicks Accept; Microsoft redirects to the registered redirect URI
   with `?code=…&state=…`.
7. `m365-oauth-callback`:
   - Verifies state HMAC + age (≤15 min)
   - Exchanges code at `/{authority}/common/oauth2/v2.0/token`
   - Decodes the unverified `id_token` body to extract `tid` (= the M365
     tenant GUID the admin came from)
   - Upserts `m365_tenants` with `consent_state='active'`
   - 302s the operator back to `/m365?connected=<tid>`

### Elevated (remediation) consent

Same flow, with `mode: "remediation"` requested. Additional scopes
appended to the consent set: `MailboxSettings.ReadWrite`,
`Directory.ReadWrite.All`, `Application.ReadWrite.All`,
`User.RevokeSessions.All`. On success the existing `m365_tenants` row is
upserted with `remediation_enabled=true`.

The remediation scopes are NOT pre-declared on the Azure AD app —
they're requested dynamically via the `scope` URL parameter. This means
the default read-only consent screen only shows read-only permissions,
which keeps the friction low for the common case.

1. **Register the Azure AD multi-tenant app** in your Mithras Azure
   tenant. Step-by-step guide is the in-app page `/guides/m365-itdr-setup`
   — it covers app registration, the seven required Graph permissions,

   `/opt/peritus-frontend/`.
4. **Smoke-test** by connecting your own M365 tenant on `/m365` and
   clicking **Poll now**.

Secrets in current `.env` (do not paste anywhere):

```
M365_STATE_SECRET     # used to sign OAuth state
M365_POLL_SECRET      # shared between pg_cron + poller; also stored in platform_settings
APP_BASE_URL          # https://www.mithras.com.au — used by callback redirect
```

### Rotation

- Azure AD client secret: rotate every 12-24 months. Paste new value into
  Settings → save. No customer re-consent required.
- `M365_POLL_SECRET`: rotate any time. Update `.env`, restart `functions`
  container, update `platform_settings.m365_poller_secret` to match.
- `M365_STATE_SECRET`: rotating invalidates any in-flight consents (≤15
  minute window); rotate during low-traffic.

## 7. Known gaps / Phase 2 candidates

- **Remediation actions UI.** Consent flow exists; the "Disable this
  forwarding rule" / "Revoke this OAuth grant" buttons are not built.
- **Stale mailbox-rule sweep.** A rule that disappears between polls
  isn't actively flagged inactive yet. Mostly harmless — the active rules
  list re-derives correctly — but the "history" view will show ghost rows.
- **Tenant-domain refresh cadence.** Tenant domain list is fetched every
  poll. Could be cached for the duration of a poll cycle to save one
  Graph call.
- **No backfill UI.** First poll fetches 6h history; older events would
  need a manual backfill function (not built).
- **No alerts → email/SMS routing for m365 events specifically.** They
  flow through the existing alerts table, so they hit the existing alert
  notification rules. If you want separate routing rules per alert
  source, that's a follow-up.

See [`BACKLOG.md`](../../../BACKLOG.md) for the full pending-work list.

## 8. Test plan

Manual smoke test once Azure AD app is registered:

1. Sign in as super-admin → Settings → Microsoft 365 / Entra ID
   integration → fill in credentials → Save.
2. Connect a test M365 tenant via `/m365`. Should land back on `/m365`
   with the new tenant in the connected list and a "Microsoft 365
   connected" toast.
3. Click **Poll now**. Within 30s the dashboard should show:
   - Sign-in events count > 0 (assuming the tenant has any activity in
     the last 6h)
   - `last_poll_at` updated
   - No `last_poll_error`
4. Optionally create a deliberately-bad mailbox forwarding rule
   (forwarding to `gmail.com`) in the test tenant → poll again →
   confirm an `m365_external_mailbox_forward` alert appears with
   critical severity.
5. Optionally consent to a high-risk OAuth app (e.g. a 3rd-party app
   asking for `Mail.ReadWrite`) → poll → confirm an
   `m365_high_risk_oauth_grant` alert appears.

Automated tests are not in place yet; given the integration depends on a
real Microsoft tenant they're worth deferring until the manual flow has
shaken out any obvious issues.
